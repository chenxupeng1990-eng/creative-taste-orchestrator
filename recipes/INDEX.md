# Production recipes

A recipe links an intended visible effect to assets, implementation, and evidence. It is not a style label or a promise that a renderer already exists. Read only the relevant card; keep project assets and private feedback in the project.

| Recipe | Route and use | Current readiness |
|---|---|---|
| [Product light stage](product-light-stage.md) | Layer-led or hybrid product hero; light, edge, contact and type integration | `production_spec`: a build procedure; no calibrated renderer or approved beauty image supplied |
| [Surface scroll study](surface-scroll.md) | Real-time surface observation and controlled cutaway | `production_spec`: requires project textures/geometry and implementation; not a skin simulator |
| [Canvas art-motion reference](canvas-art-motion.md) | Procedural painting, shared choreography, offline frame rendering | `external_source`: pinned implementation inspected at source level; not bundled or executed by this update |

## Promotion, not ceremonial metadata

Use these documentation labels only:

- `production_spec`: describes how to make and test the unit; implementation remains to be built.
- `external_source`: identifies actual source code; local compatibility and output quality remain unverified.
- `reproduced`: include the implementation entry, dependency revision, command, actual output locator, and conditions from a local run.
- `calibrated`: add the specific human-confirmed comparison, scope, and remaining defects. Calibration for one task does not certify every future task.

These labels are not new states understood by `apply_review.py`. Do not mark a card reproduced from a successful import, or calibrated from a model's own praise. A claimed reusable capability must have a usable implementation and visible example; otherwise leave it a production specification.

## Recipe shape after real production

Keep only information that changes the next attempt: intended relationship; required assets and registration; implementation/functions; influential parameters; how to render a frame and a full beat; evidence and viewing conditions; failed attempts and their fixes; performance boundary; and known weaknesses. Pin source revisions. Respect upstream notices when copying source; no fonts or private media are copied by this update.

After each useful iteration, trace `observed defect -> proposed cause -> actual edit -> visible result -> reusable home`. Domain-specific craft belongs in its card. A repeated deterministic problem belongs in a working helper plus tests. Once that helper removes the problem, shorten the duplicated prose. User preference and model diagnosis remain separate records.

Start with one excellent project unit rather than dozens of untested recipes. A successful file/QA pipeline is not a successful visual precedent.
